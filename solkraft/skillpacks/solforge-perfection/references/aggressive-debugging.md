# Perfection Aggressive Debugging Contract

## Purpose

Solve failures in the machinery used to solve the product so Perfection can continue the already-authorized work. This layer is internal to Perfection. It is not a new approval flow, a replacement product objective, or an excuse to stop after producing a diagnosis.

## Trigger immediately

Enter debugging when any of these prevents forward progress:

- a command, build, test, verifier, installer, or generator cannot run as intended;
- a required tool is missing, stale, disconnected, incorrectly registered, or returns an impossible transition;
- a sandbox, archive, temporary workspace, dependency, credential-free local service, or platform adapter is broken;
- a supposedly read-only action changes tracked files or a background process keeps mutating state;
- a test or evidence parser rejects valid output, accepts false output, invokes the wrong target, hangs, or proves something other than the intended behavior;
- Goal, receipt, checkpoint, pause/resume, or commit state prevents continuation despite existing authority;
- the plan names an action that available skills and tools cannot execute;
- the same failure signature returns after a repair, or activity continues without measurable product progress.

Ordinary product defects stay in the normal Perfection loop unless the method used to repair them is itself failing.

## Preserve before probing

Record the original objective, accepted authority, interrupted action, expected result, exact observed failure, active processes, repository revisions, pre-existing dirty paths, loop-owned paths, last good checkpoint, and the command or tool call needed to re-enter the work.

If a faulty process is still writing, stop that process first. Restore only verified files generated by the failed attempt. Never erase unrelated or user-owned work.

## Causal debugging loop

1. **Reproduce narrowly.** Reproduce the smallest instance of the exact obstruction once. Do not repeatedly run a broad suite or entire workflow just to see the same failure.
2. **Classify ownership.** Decide whether the source owner is the product, invocation, SolForge/Codex tool surface, environment, verifier/evidence contract, repository isolation, durable state/Goal transition, or plan.
3. **Compete causes.** Keep up to three materially different causal hypotheses. For each, state the observation that would distinguish it from the others.
4. **Probe economically.** Run the cheapest high-information probe. Prefer inspecting actual inputs, outputs, process state, tool inventory, revisions, and generated paths over speculative rewrites.
5. **Repair the owner.** Fix the command, runtime registration, isolation mechanism, parser, state transition, recovery dispatch, plan, or product source that actually owns the failure.
6. **Prove re-entry.** Rerun the originally blocked action or an explicitly accepted semantic equivalent. The debug repair is not complete merely because its own unit test passes.
7. **Resume immediately.** Return to the interrupted Perfection action with the same Goal and authority. Preserve the incident record as evidence, not as a new workflow gate.

## Anti-stall rules

- After one repeated identical failure, stop retrying and change the causal hypothesis or repair route.
- Never run the same probe twice unless an identified input or implementation changed.
- Never create a new Goal merely because an inner action failed. Recover the existing durable directive and lineage.
- Never substitute a generic review for a required specialized capability. Repair or expose that capability, or use only a contractually equivalent route.
- Never call generated reports or test artifacts product repairs. Restore read-only contamination before continuing.
- If one lane has a genuine external blocker, continue independent authorized lanes and preserve a precise re-entry condition for the blocked lane.
- Escalate to a major Research/Mastery checkpoint only when the repair changes architecture or public contracts, exposes a new capability family, or three distinct evidence-backed causal repairs fail. A retry counter alone is not evidence of an external blocker.

## Durable incident record

Persist, outside target repositories unless the product itself owns the diagnostic artifact:

- interrupted action and expected observable result;
- exact failure signature and classification;
- last good state and owned-path ledger;
- hypotheses, discriminating probes, and observed results;
- source-owned repair and changed paths;
- re-entry check and its actual result;
- resumed action and next progress boundary;
- remaining external uncertainty.

Do not add a standard list of actions that were not taken. Restrictions come from explicit user constraints and the accepted effect plan; accepted landing actions remain normal work.

Status is `debugging_obstruction` while diagnosis is active, `debug_repair_applied` after the mechanism changes but before re-entry succeeds, and `work_resumed` only after the original action advances. Never report the product repair or Perfection phase complete from a debugger-only check.

## Plain-language reporting

Explain what work was stuck, what mechanism failed, what exact behavior or files changed, what the operator can now do, how re-entry was demonstrated, what remains unproved, and what was not performed. Internal incident identifiers are secondary traceability only.
