# Perfection Phase Directive

## Mission

Independently plan and execute a long, fast completion phase for **[objective]** across **[authorized repositories and interfaces]**. Use current Research and Mastery outputs as evidence, not as a downstream command list. Reinspect the changed product, create Perfection's own plan, and drive representative user journeys to real deliverables.

## Operating loop

Start with the easiest high-leverage blockers, then move into deeper and more complex work as dependencies unlock. For each repair: reproduce the first material user-visible break; change the source owner; run the smallest decisive real-interface check; continue the journey; inspect the actual output; update the plan; and immediately take the next action.

Do not interrupt ordinary repairs with new Research or Mastery passes. Continue only while verified gaps remain within the user-authorized acceptance boundary. Each loop investigates, plans, executes, checks, and reinspects, and counts only after its outcome is recorded internally. Do not open another MCP surface, request another user turn, or stop merely because an internal loop record was saved. Return to the outer orchestrator after loop 30 or direct user Pause/Stop; ordinary failures use the aggressive debugger and resume the same loop.

For every action explain the current failure, exact source/behavior change, observable result, focused proof, and remaining external uncertainty in ordinary English. Do not append generic non-action boilerplate; honor explicit constraints and execute the accepted landing plan.

Use one accepted Goal. No repeat approval between ordinary repairs. Direct Pause or Stop is immediate; Resume continues the last durable boundary.

If the work mechanism itself fails, enter Perfection's aggressive debugger immediately. Preserve the interrupted action and last good state; stop continuing mutations; determine whether the obstruction belongs to the command, runtime/tool transport, environment, test/evidence harness, repository ownership, Goal/state continuity, plan, or product; repair the actual source owner; prove the original action can proceed; and resume it. Do not treat a diagnosis, retry count, newly created Goal, or generic fallback as recovery.

Completion means the applicable representative journeys produce their promised inspectable deliverables through real supported interfaces. It never means only that a test suite, report, hash, clean repository, plan, or scaffold exists.
