# DayQ Systems Design

Specify rules that can be implemented, simulated, replicated, persisted, exploited, and tested.

Read [system-sheet-contract.md](references/system-sheet-contract.md) and `../direct-dayq-content/references/dayq-canon.md`.

## Workflow

1. Confirm locked upstream decisions. Label missing inputs as provisional assumptions.
2. Map the system to player purpose and the prepare-to-extract-to-build core loop.
3. Define state, inputs, deterministic rules, stochastic rules, outputs, feedback, and failure.
4. Define progression without making early play disposable or late play safe.
5. Define cross-system dependencies, multiplayer authority, persistence fields, and relevance rules.
6. Model abuse: duplication, logout avoidance, griefing, alt accounts, permission escalation, storage exploits, economy loops, and automation edge cases.
7. Specify telemetry, prototype scope, measurable acceptance criteria, and conditions for removing the system if it only creates chores.
8. Reconcile contradictions across all affected sheets.

## Design doctrine

- Prefer interacting pressures over independent meters.
- Make physical state inspectable and repair actions concrete.
- Preserve scarcity through sources, sinks, transport, decay, loss, and contested access.
- Keep post-quantum and suppression technology bounded by recovered hardware, specialist knowledge, target intelligence, fabrication, delivery, and temporary local effects.
- Treat capturing infrastructure as the start of occupation, defense, maintenance, and political consequences.

## Output

Produce one complete sheet per system plus a dependency map and unresolved evidence list. Never omit a required field because it seems obvious.
